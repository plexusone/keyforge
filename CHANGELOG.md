## [v0.2.0] - 2026-10-25

### Highlights

- The keyring's rollback high-water mark is now authenticated under the root key, so an older keyring can no longer be put back by editing or deleting the state file beside it
- Policies must keep at least the active and the previous key version, so a rotation always leaves a rollback margin
- Two breaking changes: the first `Open` after upgrading needs `AcceptRollback` once, and `RetainVersions` below 2 is rejected

### Breaking

- The first `Open` of an existing keyring after upgrading fails with `ErrUnauthenticatedBackupState` until it is done once with `AcceptRollback` (`local.Options` or `embedded.Options`)
- Opening a keyring past generation 1 without its backup state file, for example after moving it to a new host, fails with `ErrBackupStateMissing` and needs `AcceptRollback` once
- A policy with `RetainVersions` below 2, in the default or in a per-purpose override, is rejected by `Policy.Validate` and `Set.Validate`, and so by `rotate.New`

### Upgrade Guide

- Stop the process, confirm the keyring on disk is the one you expect with `keyforge keyring inspect`, then open it once with `AcceptRollback: true` in `local.Options` or `embedded.Options`; remove the option after that first successful open
- Set `RetainVersions` to 2 or more, or leave it zero to inherit the default of 2, in the default policy and in every per-purpose override

### Security

- The local provider kept the highest keyring generation seen in plain JSON beside the keyring (`<keyring>.backup`) and read a missing file as "nothing seen". Anyone able to write the keys directory could restore an older, still validly sealed keyring and delete or edit that file, and `Open` accepted it without `AcceptRollback`, bringing back destroyed key versions or undoing a rotation. The state file is now authenticated with HMAC-SHA-256 under a key derived from the root key with HKDF and bound to the keyring's file name; `Open` refuses a state file that does not authenticate, a missing state file beside a keyring past generation 1, and a state file in the previous unauthenticated format
- Policy validation accepted a retained-versions floor of 1, which let a deployment retire the previous key version and lose the rollback margin. `RetainVersions` must now be at least 2, in the default and in every per-purpose override; a compromised version is still not counted by the floor and can be retired and destroyed at once

### Added

- `local.ErrCorruptBackupState`, `local.ErrBackupStateMissing` and `local.ErrUnauthenticatedBackupState`, returned by `Open` for a backup state file that does not authenticate, is missing beside a keyring past generation 1, or is in the previous unauthenticated format

### Changed

- Root key rotation authenticates the backup state under both the old and the new root key before replacing the keyring, so a crash on either side leaves state that the surviving keyring's root key opens
- Opening with `AcceptRollback` after one of the new backup state errors rewrites the state authenticated and keeps any existing high-water mark and backup acknowledgement

### Documentation

- Operations guide and threat model describe the authenticated backup state file, the new errors and the upgrade step; the policy table states the retained-versions floor of 2

## [v0.1.0] - 2026-10-12

### Highlights

- Envelope encryption for Go: data keys wrapped by provider-held key-encryption keys, so a key-encryption key can rotate without re-encrypting stored data
- Guarded retirement and destruction: a caller-supplied guard can veto, a delay applies, and every outcome is audited
- Per-subject keys make erasure a key destruction, with completion tracked until every key version that wrapped the subject's keys is gone
- A single-host setup from a directory and a root key (`embedded.Open`), with a SQLite registry; PostgreSQL is supported for shared deployments
- Not externally audited and not yet recommended for production use; the envelope format is frozen from this release

### Security

- Internal review of the data path and of the lifecycle and storage layers; findings fixed before release (cache state across purge, compromise and destruction; a keyring restored under a running process; shredding under an unknown purpose; error text in status reports; file permissions)
- Known limitations are listed in the threat model, including that a restore can undo an erasure and that inline wraps are not counted per key-encryption key version

### Added

- Envelope format version 1 with reference and inline modes, a canonical text form (`kf1.`), AAD binding purpose, mode, key identity and caller context, and published known-answer vectors
- Client: `Encrypt`, `EncryptFor`, `EncryptInline`, `Decrypt`, `Reencrypt`, `AdvanceEpoch`, `Verify` and `Purge`, with a bounded key cache, a per-key encryption cap enforced across replicas and crashes, and data key epochs by volume and age
- Algorithm registry and profiles: AES-256-GCM through `cipher.NewGCMWithRandomNonce`, a `standard` and a `fips` profile that configuration can only narrow, and code that stays valid under `GODEBUG=fips140=only`
- Provider interface with a conformance suite, an in-memory provider, and a keyring-file provider sealed under a root key, with atomic writes, locking, a generation counter, rollback detection and backup acknowledgement
- Registry with a transition table for key versions and data keys, and an Ent-backed SQL store for SQLite and PostgreSQL (pgx) that passes the store conformance suite on both
- KEK rotation with sentinels, resumable re-wrapping, rollback, guarded retirement with a delay, destruction, and emergency procedures for an exposed key-encryption key or data key
- Per-subject keys and crypto-shredding with a tombstone and completion tracked against the key versions that ever wrapped the subject's keys
- Lifecycle scheduler on OmniWorkflow: deterministic run identifiers, backoff, and resumption after a restart
- HTTP control plane with an authorizer asked before every action, an audit trail, a status report with health and a metrics interface, and a Cobra command line over it (`status`, `rotate`, `rewrap`, `retire`, `destroy`, `compromise`, `shred`, `backup ack`, `verify`, `health`)
- `embedded` package: keyring, SQLite registry, jobs and control plane wired from a directory and a root key source, with idempotent first start and consistent registry backup
- Documentation: getting started, operations, envelope format, threat model, and the product and technical requirements
- Import-boundary test: the packages that touch key material import only the standard library and oscompat, a dependency-free module for operating-system differences
